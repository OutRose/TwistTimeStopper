- **§2 必須項目 4 (壊し確認・Red 先行)**: この一文があるかどうかで成果物の品質が目に見えて安定した (M3〜M7 の実績)。
- **§2 確定済み判断の列挙**: M8 (機能1第二層、SPEC ベースの委譲 3 回) では各プロンプトに確定済み判断を 6〜10 項目列挙し、3 回とも差し戻しゼロ・受け手の独自判断ゼロだった。列挙しない場合、受け手が仕様の解釈で止まる (差し戻し往復) か、勝手に埋める (レビューで発覚) かの二択になる。

- **§6 メイン側修正でも TDD**: M8 で parse_full の欠落ファイル失敗様式の不統一をこの手順で修正 — Red の実行結果が「指摘が実在した」証拠と「回帰しない」保証を同時に残す。
- **原則 6 (待機禁止・停止=通知) / §2 必須項目 5 (実行時間の目安 + timeout 明示) / §5 (停止通知の振り分け)**: Racing-Predictor (2026-07-29) で、検証ゲート (実行 120 秒超) が Bash 既定タイムアウトで自動バックグラウンド化され、implementer が「検証待ち」で停止 → SendMessage「同期実行せよ」でも timeout 未指定のため再停止、のループが繰り返し発生。公式ドキュメント上、subagent はユーザーへ質問する手段を持たず (AskUserQuestion は強制除去)、subagent のバックグラウンドシェルは 60 分で強制終了され、バックグラウンドコマンドの完了で subagent を再起動する機構の記載も無い (= 実質孤児化。ここまで公式記載) ため、ターンを維持したままの待機は成立しない (結論は推論)。「最終報告で停止 → メイン対応後に SendMessage で文脈保持のまま自動再開」が公式の第一級パターン (code.claude.com/docs/en/sub-agents「Resume subagents」)。timeout の目安 2 倍・上限 600000ms、BASH_DEFAULT_TIMEOUT_MS / BASH_MAX_TIMEOUT_MS は tools-reference / env-vars で確認。状態行 (完了 / 要対応) は、停止が完了通知としてしか見えず要対応停止の検知が遅れる問題への対処。
