# implementer 委譲の標準手順

モデル分業方針 (~/.claude/CLAUDE.md) の実行手順。各項目は APKExplorer M3〜M8 の委譲 15 回で実際に起きた失敗・成功に由来する (詳細な出典は同ディレクトリの rationale.md)。

`/implementer-delegation` だけが送られ、現在の依頼や会話に対象と確定仕様が無い場合は、作業ツリーや周辺ファイルを調べず、「委譲する対象と確定仕様を教えてください。」と一文だけ返して終了する。ファイル名・既存変更・仕様を推測して補わない。既に具体的な作業指示がある場合はそのまま以下へ進む。仕様のない探索は委譲前の使用量だけを増やす。

**この手順は Anthropic Claude (Claude Code) 前提。** サブエージェントを起動する Agent ツール (`subagent_type`)、実行中・停止済みエージェントへ指示を送る SendMessage、TaskStop、Bash の timeout 指定といった Claude Code 固有の機構に依存する。これらを持たない環境 (Cursor・Codex 等) でこの Skill が読み込まれた場合は、委譲そのものが成立しない — §2 の必須項目を「自分が着手前に書き下すべき作業仕様」として使い、実装後に §6 の検証を自分で行う劣化動作に切り替える。

## 1. 委譲してよいか判定する

**委譲する**: 仕様が確定したモジュールの実装 / テストコード作成 / 機械的な修正・リファクタ。

**委譲しない**: 仕様が曖昧な段階の探索・設計 / 判断が重い工程 / コミット・マージ判断 / 数回のツール呼び出しで終わる作業 / 自分の成果物の検証。

迷ったときの目安は「**受け手が設計判断ゼロで完遂できる仕様を、いま書き下せるか**」。書けないならまだ委譲段階ではない — 先に仕様を固める (それはメイン側の仕事)。

## 2. 委譲プロンプトを組み立てる

サブエージェントは**会話の文脈を一切持たない**。合意事項・調査で判明した事実は、すべて本文へ書き下すか参照先パスを明示する。「前述の」「さっき決めたとおり」は書いた時点で欠陥。

### 必須 7 項目 (1 つでも欠けたら送らない)

1. **対象プロジェクトのルートパス** と、変更対象・新規作成ファイルのパス列挙
2. **「最初に対象プロジェクトの CLAUDE.md を読む」指示** + 今回のタスクに特に関係する規約の § 番号と要旨 (受け手に全文精読と取捨選択をさせない)
3. **「~/.claude/checklists/INDEX.md を読み、§<該当カテゴリ番号> の詳細ファイルに従うこと」の一文** — 該当カテゴリはメイン側が選んで指定する (受け手に全カテゴリを読ませない)。implementer 以外へ代替委譲するときも漏らさない
4. **期待するテスト内容**。TDD 案件は Red→Green の順序を明示。バグ修正は「**修正前に Red (再現テストの失敗) を確認**してから直す」、テスト補強は「**実装を一時的に壊してテストが赤になることを確認 (壊し確認) してから戻す**」まで指示する
5. **検証コマンド** (対象プロジェクトの CLAUDE.md が定める検証ゲート) + 「**生の実行結果を残す**」。Red・Green・最終検証の stdout / stderr 全文は作業ツリー外の別々の一時ログへ保存し、終了コードと絶対パスを報告させる。全文転載が指定されていればログをそのまま報告へ載せる。要約された「通りました」は検証の証拠にならない。**実行時間の目安も書く** — 120 秒 (Bash 既定タイムアウト) を超えるゲートは「timeout に目安の 2 倍を明示指定して同期実行」まで指示する (未指定のままだと自動バックグラウンド化 → 検証待ち停止ループになる)。timeout の指定上限は 10 分 (600000ms) のため、**目安 5 分超のゲートは 2 倍の余裕が取れない** — implementer には対象モジュールに絞った部分ゲートを指定し、フルゲートは §6 のメイン側検証で実行する。目安が不明なら委譲前にメイン側で一度実行して計測する (どのみち §6 で再実行するので無駄にならない)
6. **コミット禁止の明示** (コミットはメイン側の責務)
7. **報告フォーマット**: 冒頭の状態行 (完了 / 要対応) / 変更ファイル一覧 / テスト・検証ログの絶対パスと終了コード / 設計判断が必要で止めた論点

### 仕様書ベースの案件では「確定済み判断」を列挙する

確定済みの仕様書 (SPEC 等) があるときは、全文を貼り込まず**仕様書のパス + 今回読むべき § 番号**を指定して受け手に読ませる。そのうえで、仕様書に残る曖昧点・矛盾点は**委譲前にメイン側で解決し切り**、「メイン側で確定済みの判断 (これに従う。独自解釈しない)」として番号付き列挙する。仕様書が規範コードを含むならどのコード片が規範かも指す。曖昧点を書き下せないなら §1 の「まだ委譲段階ではない」シグナル。

### テンプレート

```markdown
## 委譲タスク: <一言サマリ>

対象プロジェクト: <ルートパス>

最初に <ルートパス>/CLAUDE.md を読み、規約に従うこと。今回特に関係する規約:
- §<番号>: <要旨>
~/.claude/checklists/INDEX.md を読み、§<該当カテゴリ番号> の詳細ファイルに従うこと。

### 目的
<何を達成するか 1〜3 文。背景の合意事項もここに書き下す。仕様書がある場合はパスと該当 § を指定>

### メイン側で確定済みの判断 (仕様書ベースの案件のみ。これに従う。独自解釈しない)
1. <仕様書の曖昧点に対するメイン側の解決>
2. <実装方式・評価順・エラー文言など、受け手に選ばせない決定>

### 対象ファイル
- 変更: <path> — <何をどう変えるか>
- 新規: <path> — <役割>

### 仕様
<設計判断を残さない粒度で: データ型・シグネチャ・エラー時の挙動・境界値・表示文言>

### テスト
- <期待するテストを列挙>
- TDD: Red (失敗するテスト) を先に書き、失敗を確認してから実装する
- (テスト補強の場合) 実装を一時的に壊してテストが赤になることを確認してから戻す (壊し確認)

### 検証
- <検証コマンド> を実行し、Red・Green・最終検証の生ログを作業ツリー外へ個別に保存する。報告に絶対パスと終了コードを含め、全文転載の指定があれば省略せず貼る
- 検証コマンドはバックグラウンド実行 (run_in_background) にしない
- (120 秒超のゲートのみ) 実行時間の目安: 約 <N> 分。Bash の timeout に <N の 2 倍> 分 (上限 10 分) を明示指定して同期実行する

### 制約
- コミットしない (メイン側で行う)
- 設計判断が必要な曖昧さを見つけたら、勝手に決めずに作業を止めて差し戻す
- メイン側の検証・判断が必要になったら、ターン内で待機せず、状況を報告して即ターンを終了する (停止 = メインへの通知。対応後に SendMessage で再開される)

### 報告
冒頭に状態行 (`状態: 完了` / `状態: 要対応 (差し戻し | 検証引き継ぎ)`) / 変更ファイル一覧 / テスト・検証ログの絶対パスと終了コード / 差し戻し論点・気づいた問題
```

## 3. 委譲を実行する

- Agent ツールで `subagent_type: "implementer"` を指定する (model はエージェント定義側で固定済み — 呼び出し側で指定し直さない)。implementer が利用できない環境では general-purpose + `model: "sonnet"` で代替し、~/.claude/agents/implementer.md の原則をプロンプト冒頭へ貼り込む
- 複数の委譲を並行させてよいのは**変更ファイルが重ならないときだけ**。重なるなら直列にするか、`isolation: "worktree"` で分離する
- **大きい機能は直列の段階へ分割し**、各段階の完了ごとに §6 の検証・コミットを済ませてから次段階を委譲する (段階境界 = 検証ゲートが通る単位のコミット粒度)。**後続段階のプロンプトには前段階の成果 (新設 API のシグネチャ・挙動・格納先) を書き下す** — 受け手は前段階の委譲会話を知らない
- バックグラウンド実行が既定。完了待ちの間、メイン側はファイルが重ならない作業を並行してよい
- 検証ゲートが恒常的に 120 秒を超えるプロジェクトでは、対象プロジェクトの `.claude/settings.json` の `env` で `BASH_DEFAULT_TIMEOUT_MS` (既定 120000) を引き上げる恒久策も検討する (上限側は `BASH_MAX_TIMEOUT_MS`、既定 600000。サブエージェントへの適用は明文化されていないが settings の env はセッション全体に効く)

## 4. 実行中のエージェントへの追加指示 (罠に注意)

実行中のエージェントへの追加指示・訂正は **SendMessage (to: agentId)** を使う。**Agent ツールを再度呼んではならない** — 文脈を持たない別の新規エージェントが起動するだけで、元のエージェントは指示を受け取れないまま走り続ける (M7 で実際に発生した事故)。

誤って Agent ツールで起動してしまったら: TaskStop で新規側を即停止 → SendMessage で正しい agentId へ送り直す。

## 5. 停止通知を受けたら — 状態行で振り分け、放置しない

implementer の停止 (最終報告) は完了とは限らない。停止への対応は新規作業より優先する (放置した時間だけ委譲パイプライン全体が止まる):

- **状態: 完了** → §6 の成果物検証へ
- **要対応 (差し戻し)** → 先に設計判断を下し、SendMessage で判断を送って再開する (§6-4。判断せずに自分でコードを直し始めない)
- **要対応 (検証引き継ぎ)** → 検証コマンドがバックグラウンド化されたまま停止した状態。バックグラウンドのコマンドは完了しても implementer を再起動しない (孤児化) ため、検証はメイン側で引き取る: implementer 側のコマンドが残っていれば先に停止し (同一ゲートの並行実行を作らない)、ゲートをメイン側で実行する。通ったら完了報告と同等に扱い §6 の 2 以降 (diff レビュー〜コミット判断) を実施する。実装の残作業があるなら検証結果を添えて SendMessage で再開する
- **罠**: 検証待ち停止に「同期実行して待て」と再開指示するだけでは直らない — timeout 未指定のままでは再び 120 秒でバックグラウンド化され、同じ停止を繰り返す (Racing-Predictor 2026-07-29 実測)。再開指示には timeout の明示指定を含める

再開は必ず SendMessage (§4)。停止済み (completed) のサブエージェントも SendMessage で文脈を保持したまま自動再開する — 停止をコストと考えて implementer 側に待機させない。

## 6. 成果物を検証する (報告を鵜呑みにしない)

完了報告を受けたら (§5 の検証引き継ぎをメイン側で完了させた場合も同様に)、コミット・マージ判断の前にメイン側で必ず:

1. **子が報告した Red・Green・最終検証のログを実ファイルで確認し、検証ゲートを自分で再実行する** (生ログ付き報告でも、報告後の手直しで壊れていることがある)。ログが欠けていれば子の検証報告は未確認として扱い、必要な Red を自分で再現して記録する
2. **diff を自分でレビューする**。~/.claude/checklists/INDEX.md のカテゴリを観点に使う
3. テスト補強案件では**壊し確認の実施が報告されているか**確かめる。なければ SendMessage で追加指示するか、自分で実装を一時的に壊して赤を確認する
4. **差し戻し論点が報告されていたら、先に設計判断を下す**。判断せずに自分でコードを直し始めない (受け手の作業と二重変更になる)
5. **メイン側で直すときも TDD を省略しない**。検証で見つけた欠陥は、失敗様式を固定するテストの Red を確認してから直す
6. **コミット・マージ判断はメインの責務**として自分で行う

検証ゲート全通過の委譲実装からも、マージ前レビューで毎回確定修正が出ている (M3〜M7 で各 10〜16 件) — ゲートが緑でもレビューは省略しない。
