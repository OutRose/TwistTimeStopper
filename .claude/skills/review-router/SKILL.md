# review-router

コードレビュー依頼を、変更の規模と種別に応じて適切な実行主体に振り分ける。

レビュー依頼では、この Skill を必ず起動する。後述の「直接レビュー」は subagent を省く条件であり、Skill の省略条件ではない。

## 実行主体

| 主体 | 役割 | 起動方法 |
|---|---|---|
| **review-light** | フォーマット・命名規約・typo・import順・未使用変数など機械的に判定できる項目、および大量ファイルの初期スキャン | Agent ツール `subagent_type: "review-light"` |
| **review-mid** | 実装レベルのバグ検出・ロジック検証・テストカバレッジ確認・リファクタリング提案などの標準レビュー | Agent ツール `subagent_type: "review-mid"` |
| **orchestrator自身** | モジュール横断の影響分析、アーキテクチャ判断、公開APIの互換性判断など、委譲できない重い判断 | 自分で diff を読んでレビューする |

「orchestrator自身」とは、モデルを問わず**この Skill を読んでいる本体**を指す。subagent を起動する手段が無い環境でこの Skill が読み込まれた場合は、振り分け表を自分自身のレビュー深度の配分として適用する。

## 0. チェックリストを探す

1. プロジェクトルートの `REVIEW_CHECKLIST.md` を探す
2. なければ `.claude/REVIEW_CHECKLIST.md` を探す
3. どちらも無ければ、**その旨を出力に明示した上で**、一般的な観点 (正しさ / 保守性 / セキュリティ / テストカバレッジ / 命名・スタイル) でレビューする

`~/.claude/checklists/` (ホームディレクトリ直下のグローバル版) は implementer 委譲向けの別文脈のファイルであり、この手順の代用にしない。参照した場合は「プロジェクト固有の REVIEW_CHECKLIST.md は無く、代わりにグローバル版の§◯◯を参照した」と出力上で必ず開示する。

見つかったチェックリストは、**該当カテゴリの項目をテキストとして委譲プロンプトに転記する** (subagent は会話文脈もチェックリストの実体も持たない前提で書く。パス指定は補助情報)。

## 1. 規模・種別を判定する

曖昧な依頼 (git diff / git status 直後、PR番号のみ等) は、まず diff の対象ファイル一覧・変更行数 (PRなら `gh pr diff` 等) を取得してから判定する。曖昧なまま規模を仮定しない。

- **規模**: 変更ファイル数、変更行数
- **種別**: 単一ファイル/単一モジュール内で閉じるか、モジュール横断・アーキテクチャ影響・公開API変更を含むか

種別が「モジュール横断・アーキテクチャ影響・公開API変更」に該当する場合、規模に関わらず **orchestrator自身が直接レビューする** (1ファイルの変更でも公開APIのシグネチャ変更なら該当)。変更された関数の呼び出し元も確認し、公開APIの変更かどうかを判定する。

## 2. 規模でルーティングする (種別が単一モジュール内に閉じる場合)

| 条件 | ルーティング |
|---|---|
| 20ファイル以上のdiff | review-light を並列起動 (上限3から開始) して機械的項目を先行処理 → 指摘を集約して review-mid に委譲 (同じファイルを再度ゼロからスキャンさせない) |
| 正常系の境界条件・分岐・API契約が変わる単一モジュール内のdiff | 行数が少なくても review-mid |
| ユーザーのレビュー依頼文に差分全文が含まれる数行規模の極小diff (上記の条件に該当しない場合) | orchestrator が直接レビューしてよい |
| 変更ファイルが単一、かつ50行以下 | review-light のみ |
| 単一モジュール内の複数ファイル、または単一ファイルで50行を超える変更 | review-mid |

上から優先して判定する。diff をツールで取得・閲覧したことで「会話に全文が見えている極小diff」に変更されたとは扱わない。元の依頼文に差分全文が無い場合、後から差分を読み切っても指定の subagent を起動する。20ファイル以上では各変更が1行ずつでも review-light の先行スキャンと review-mid の確認を行う。

格上げの基準は「なんとなくロジックっぽい」という印象ではなく、**既存の正常な入力に対する判定・契約 (分岐、境界条件、戻り値の意味) が変わるかどうか**。表示文言の単純な typo・命名・書式の誤りは、この格上げ条件に含めない:

- **review-mid へ格上げする**: 境界条件の判定式の変更 (`<=` → `<` 等)、正常系の戻り値の意味・契約の変更。小さい diff でも review-light の手には負えない
- **review-light のままでよい**: 異常系・想定外入力 (null、欠落属性など) へのガード節・防御的チェックの追加。正常系の挙動を変えない堅牢化はこちら。review-light がその中にセキュリティ上の懸念 (例: 不正データの黙殺) を見つけたら「要review-mid確認」と一言添えて引き継げばよく、案件全体の格上げは不要

判定に迷うときは表のとおり規模だけで決める。格上げの常態化は review-light を用意した意味を失わせる。20ファイル以上の review-mid は、先行スキャンの指摘を検証し、正常系の挙動と見落としを確認する。

## 3. 「深く見て」指定は orchestrator自身の関与を重くする

「深く見て」「じっくり」「丁寧に」等の明示があれば、1・2の判定結果に関わらず orchestrator自身の関与を一段重くする。中身 (subagent の指摘の裏取りに留めるか、diff を直接読み込むか) は対象の規模・影響範囲・リスクから判断する。委譲の省略を意味しない — 大規模diffの review-light 先行スキャンは継続してよい。

## 4. 委譲プロンプトに含めるもの

委譲プロンプトは自己完結させる (subagent は会話文脈を持たない):

- 対象ファイルパスと実際の diff。長い場合も対象範囲の差分を渡し、現在のファイルパスだけや実行できない `git diff` コマンドだけで済ませない (review-light / review-mid の許可ツールは Read、Grep、Glob)
- 該当カテゴリの REVIEW_CHECKLIST.md 項目の転記 (無ければ「チェックリストなし、一般的観点で」と明記)
- 期待する出力形式 (下記「出力フォーマット」の1〜4の粒度)
- review-mid への委譲時、review-light の先行結果があればその要約

## 出力フォーマット

統合結果は以下の順で並べる:

1. **重大度**: critical / major / minor (この順に並べる)
2. **カテゴリ**: architecture / logic / style / security / other
3. **ファイル名:行番号**
4. **指摘内容と推奨修正**

複数の主体の指摘は実行主体ごとに分けずに一本化し、同じ原因による隣接行・同一箇所への重複指摘はマージする。

**行番号は省略しない。** 実ファイルが読めない場合も diff の hunk ヘッダから対象範囲の開始行を逆算し、`manifest_parser.py:42付近 (diffのhunkヘッダ由来)` の形で示す。関数名・メソッド名で代用しない。

**minor 判定の指摘も critical/major と同じ厳密さで書く。** 具体的に何をどう直すかを推奨修正として明示する。minor は「後回しにしてよい」であって「言うだけ言って終わり」ではない。

末尾に、起動した subagent の一覧 (review-light ×N、review-mid ×N、なければ「orchestrator直接のみ」) と、消費トークンの粗い概算 (概算である旨を併記する) を付ける。
